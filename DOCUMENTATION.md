# 📄 Документація проєкту: Conference Room Booking API

---

## 1. Опис бізнес-завдань

Проєкт являє собою бекенд-систему (REST API) для автоматизації сервісу оренди конференц-залів та додаткових супутніх послуг.

### Основні бізнес-вимоги та функціонал:
1. **Управління конференц-залами (CRUD)**:
   - Створення залів з індивідуальними характеристиками: назва, максимальна місткість (кількість осіб), базова погодинна ставка оренди.
   - Закріплення за кожним залом каталогу доступних послуг (Wi-Fi, мультимедійний проєктор, аудіообладнання, кейтеринг, відеозв'язок) з фіксованою ціною.
   - Можливість редагування параметрів залу, оновлення списку закріплених послуг та видалення залів.

2. **Пошук вільних приміщень**:
   - Фільтрація залів за необхідною місткістю та бажаним інтервалом оренди (дата/час початку та тривалість у хвилинах).
   - Автоматичний контроль зайнятості та виключення залів, що мають часові перетини з наявними бронюваннями.

3. **Динамічне ціноутворення оренди**:
   - Автоматичний погодинний розрахунок вартості на основі часу доби:
     - **06:00 – 09:00**: Ранкова знижка 10% (коефіцієнт `0.90`)
     - **09:00 – 12:00**: Стандартний тариф (коефіцієнт `1.00`)
     - **12:00 – 14:00**: Піковий час +15% (коефіцієнт `1.15`)
     - **14:00 – 18:00**: Стандартний тариф (коефіцієнт `1.00`)
     - **18:00 – 23:00**: Вечірня знижка 20% (коефіцієнт `0.80`)
     - **23:00 – 06:00**: Стандартна ставка (коефіцієнт `1.00`)
   - Додавання фіксованої вартості обраних послуг до суми оренди.
   - Збереження зліпка цін послуг на момент створення замовлення для фінансової цілісності історії.

4. **Аналітична звітність**:
   - **Звіт виручки** (`/api/reports/revenue`): загальний дохід, кількість замовлень та середній чек по кожному залу за обраний часовий період.
   - **Звіт завантаженості** (`/api/reports/utilization`): сумарна кількість фактично заброньованих годин та кількість бронювань по кожному залу.
   - **Рейтинг послуг** (`/api/reports/services`): популярність додаткових послуг (кількість замовлень) та згенерований ними дохід.

## 2. Архітектурні та технічні рішення

### 2.1. Архітектурний підхід: Clean Architecture & DDD
Система розділена на 4 ізольованих шари:
1. **Domain Layer (`ConferenceBooking.Domain`)**:
   - Не залежить від жодних зовнішніх бібліотек, фреймворків чи БД.
   - Містить сутності `Room`, `Booking`, `Service`, `BookingSelectedService`, `RoomServiceItem`.
   - Містить доменні винятки (`NotFoundException`, `RoomUnavailableException`, `DomainValidationException`).
   - Містить чистий доменний сервіс розрахунку тарифів `PricingDomainService` та інтерфейс `IPricingDomainService`.
2. **Application Layer (`ConferenceBooking.Application`)**:
   - Сценарії використання системи: `RoomService`, `BookingService`, `ReportService`.
   - Інтерфейси репозиторіїв та бізнес-сервісів.
   - DTO моделі запитів/відповідей із валідацією атрибутами `System.ComponentModel.DataAnnotations`.
3. **Infrastructure Layer (`ConferenceBooking.Infrastructure`)**:
   - Реалізація доступу до даних через **Entity Framework Core 10** та **SQLite**.
   - `AppDbContext` із конфігурацією реляційних зв'язків через Fluent API (`Cascade` для прив'язок залу та `Restrict` для захисту історії замовлень послуг).
   - Реалізація патерну Репозиторій (`RoomRepository`, `BookingRepository`, `ServiceRepository`).
   - Автоматичний Seeder (`SeedData`) для створення БД та заповнення тестовими даними при першому старті.
4. **Presentation Layer (`ConferenceBooking.Api`)**:
   - ASP.NET Core Web API контролери (`RoomsController`, `BookingsController`, `ReportsController`).
   - Глобальний `ExceptionHandlingMiddleware` для перехоплення помилок та повернення стандартизованих JSON відповідей (`RFC-7807` style).
   - Налаштування Swagger / OpenAPI з інтеграцією XML-документації з усіх шарів.

### 2.2. Алгоритмічні рішення:
1. **Контроль часових колізій (Collision Detection)**:
   - Застосовано сувору формулу перетину інтервалів:
     $$\text{Collision} \iff (\text{Booking.StartTime} < \text{RequestedEnd}) \land (\text{Booking.EndTime} > \text{RequestedStart})$$
   - Дозволяє безпомилково обробляти будь-які варіанти перекриття та стикування інтервалів хвилина-в-хвилину.
2. **Погодинне сегментування тарифів із підтримкою переходу через північ**:
   - Інтервал розбивається по календарних днях (`while (current < endTime)`).
   - У межах кожного дня час нарізається на підінтервали за тарифними зонами, рахується точна частка годин у хвилинах та множиться на відповідний коефіцієнт.
3. **Захист від проблеми N+1 запитів у звітності**:
   - В `ReportService` дані залів та бронювань вивантажуються одним оптимізованим запитом із групуванням у пам'яті через `Dictionary<Guid, List<Booking>>`.

## 3. Специфікація REST API

| Метод | Маршрут | Опис | Параметри запиту | Статус-коди |
| :--- | :--- | :--- | :--- | :---: |
| `GET` | `/api/rooms` | Отримати всі зали з послугами | — | `200` |
| `GET` | `/api/rooms/{id}` | Детальна інформація про зал | `id` (GUID) | `200`, `404` |
| `POST` | `/api/rooms` | Створити новий конференц-зал | Body: `CreateRoomDto` | `201`, `400` |
| `PUT` | `/api/rooms/{id}` | Оновити параметри залу | `id` (GUID), Body: `UpdateRoomDto` | `200`, `400`, `404` |
| `DELETE` | `/api/rooms/{id}` | Видалити зал | `id` (GUID) | `204`, `404` |
| `GET` | `/api/rooms/available` | Пошук вільних залів | Query: `startTime`, `durationMinutes`, `capacity` | `200` |
| `POST` | `/api/bookings` | Оформити бронювання з динамічним розрахунком | Body: `CreateBookingDto` | `201`, `400`, `404` |
| `GET` | `/api/reports/revenue` | Звіт виручки та середнього чека | Query: `from`, `to` (опціонально) | `200` |
| `GET` | `/api/reports/utilization` | Звіт завантаженості залів (години/кількість) | Query: `from`, `to` (опціонально) | `200` |
| `GET` | `/api/reports/services` | Рейтинг популярності та виручки послуг | Query: `from`, `to` (опціонально) | `200` |

## 4. Документування коду та Swagger (OpenAPI)

1. **XML-документація**:
   - Увімкнено генерацію XML-файлів у `ConferenceBooking.Api`, `ConferenceBooking.Application` та `ConferenceBooking.Domain`.
   - Усі контролери, дії, DTO-моделі та їхні властивості задокументовані через теги `<summary>`, `<param>`, `<returns>`, `<response>`, `<remarks>`, `<example>`.
2. **Swagger UI**:
   - Доступний за адресою [http://localhost:5162/swagger](http://localhost:5162/swagger).
   - Містить опис системи, тарифних коефіцієнтів доби, опис усіх схем запитів і відповідей та статус-кодів.

## 5. Інструкція із запуску та тестування

dotnet test
